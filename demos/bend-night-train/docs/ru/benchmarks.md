# Бенчмарки: параллелизм Bend 2 на реальной нагрузке

Все числа ниже получены на этой машине и воспроизводятся командами из текста.
Сырые данные — `bench/results.csv` (54 запуска).

## Стенд

| | |
|---|---|
| CPU | Intel Core i9-14900HX, 24 физических ядра |
| Логических CPU | 32 (`nproc` → 32), по два аппаратных потока на ядро (SMT) |
| RAM | 125 ГиБ |
| Частоты | `intel_pstate`, на время свипа governor выставлен в `performance` (в покое хост живёт на `powersave`), турбо включён, частота не закреплена |
| clang | 18.1.3 |
| Bend | 2.0.5, запуск через `tools/bend` |
| Нагрузка | `src/main.bend` — растеризатор: 4-арный параллельный обход квадродерева, на лист один тайл пикселей |

Кадр — это квадродерево глубины `d`, то есть `2^d × 2^d` пикселей. Глубины
8 / 9 / 10 — это 65 536 / 262 144 / 1 048 576 пикселей. В отличие от прежнего
рей-марчера, лист здесь не пиксель, а тайл 8×8, несущий треугольники, до
которых дотягивается его экранный бокс; поэтому дерево имеет глубину `d - 3`.

## Метод

```sh
make build
REPS=3 ./bench/bench.sh out/night-train bench/results.csv
```

`bench/bench.sh` прогоняет каждую ячейку `(глубина, потоки)` три раза, после
одного прогревочного прохода, и замеряет каждый запуск через
`/usr/bin/time -f "%e %U"`. Во всех запусках `NT_PPM=0`, поэтому ввод-вывод PPM
не замеряется. Число ниже — медиана из трёх прогонов. Полоса ровно одна:
в рендере нет вызова `!`, поэтому `--backend`, `--bang` и `--gpu` больше не
существуют.

Для разрешения тоньше, чем сантисекунды `/usr/bin/time`, `bench/measure.py`
повторяет одну команду с `perf_counter` и `getrusage` и печатает медиану:

```sh
python3 bench/measure.py --reps 5 --env NT_DEPTH=10 --env NT_PPM=0 -- ./out/night-train --threads 8
```

## 1. Масштабирование по ядрам

`bench/results.csv`, медиана из 3 прогонов, секунды. В каждой ячейке
`wall_s / user_s / (user_s ÷ wall_s)`:

| глубина | t=1 | t=2 | t=4 | t=8 | t=16 | t=32 | контрольный код |
|---|---|---|---|---|---|---|---|
| 8 (256²) | 0.360 / 0.33 / 0.92 | 0.260 / 0.39 / 1.50 | 0.220 / 0.44 / 2.00 | 0.200 / 0.47 / 2.35 | 0.190 / 0.48 / 2.53 | 0.160 / 0.49 / 3.06 | 299380445 |
| 9 (512²) | 0.660 / 0.62 / 0.94 | 0.400 / 0.67 / 1.68 | 0.290 / 0.72 / 2.48 | 0.240 / 0.76 / 3.17 | 0.230 / 0.84 / 3.65 | 0.190 / 0.92 / 4.84 | 1065901264 |
| 10 (1024²) | 1.660 / 1.63 / 0.98 | 0.900 / 1.65 / 1.83 | 0.580 / 1.71 / 2.95 | 0.430 / 1.79 / 4.16 | 0.370 / 2.05 / 5.54 | 0.310 / 2.55 / 8.23 | 3959815329 |

Ускорение на 32 потоках: глубина 8 = 2.3×, глубина 9 = 3.5×, глубина 10 = 5.4×.
Wall-время падает вплоть до 32 потоков; потолка нет.

![Wall-время против числа потоков для глубин 8, 9 и 10; на глубине 10 падает с 1.66 с до 0.31 с](../../assets/readme/bench-scaling.svg)

*Те же числа картинкой. Дайджест — одно значение на глубину при любом числе потоков,
так что форма кривых — это работа планировщика, а не изменение картинки.*

## 2. Куда уходит процессорное время

Суммарный CPU растёт куда медленнее ускорения, а не быстрее:

| глубина | CPU на 1 потоке | CPU на 32 потоках | рост CPU | выигрыш по wall |
|---|---|---|---|---|
| 8 | 0.33 с | 0.49 с | 1.5× | 2.3× |
| 9 | 0.62 с | 0.92 с | 1.5× | 3.5× |
| 10 | 1.63 с | 2.55 с | 1.6× | 5.4× |

На глубине 10 суммарный CPU вырастает на 56 %, тогда как wall падает в 5.4×,
а `user ÷ wall` на 32 потоках доходит до 8.2. (Рей-марчер, для сравнения,
упирался в 2.7× при восьмикратном росте CPU.)

Что об этом говорит исходник: лист дерева — тайл 8×8, и `Frame.build`
отдаёт каждому листу только те треугольники (`Tri.keep`) и билборды
(`Spr.keep`), чьи экранные границы дотягиваются до этого тайла. Затем каждый
пиксель тайла один раз проходит этот короткий список и затеняется не более
чем одним треугольником, поэтому стоимость листа ограничена числом его
пикселей, умноженным на малый локальный список, — а не марчем по пикселю,
длина которого зависит от того, что встретил луч. Это согласуется с
измеренным поведением: потоки продолжают помогать, а CPU растёт медленно.
Сам планировщик не профилировался, поэтому никаких утверждений о том, почему
он ведёт себя так при данном числе потоков, здесь нет.

## 3. Проверка чистоты

Все 54 запуска дали ровно один контрольный код на глубину, независимо от
числа потоков:

| глубина | пикселей | контрольный код |
|---|---|---|
| 8 | 65 536 | 299380445 |
| 9 | 262 144 | 1065901264 |
| 10 | 1 048 576 | 3959815329 |

`Raster.digest` сворачивает кадр через `Frame.sum`, который складывает
перемешанный хэш каждого пикселя (`Frame.hash1`). Сложение коммутативно,
поэтому равные коды доказывают совпадение **множества** пикселей, а не их
расположения; расположение проверяется глазами по кадрам в `assets/frames/`.
Равенство кодов при разном числе потоков и есть проверка корректности
параллелизма: картинка не зависит от порядка обхода.

## 4. Границы измерения

- `/usr/bin/time %e` печатает сантисекунды, поэтому каждое значение wall и user несёт квант 10 мс. На глубине 8 в один поток (0.36 с) это около 3 % числа, и меньшие различия не разрешаются.
- Три прогона на ячейку, только медиана. Разброс и доверительный интервал не приводятся.
- 32 логических CPU — это 24 физических ядра с SMT. Число потоков выше 16 попадает на аппаратные потоки, а не на дополнительные ядра, поэтому часть кривой выше 16 — это SMT, а не новые ядра.
- Перед свипом governor выставлен в `performance`: в покое хост живёт на `powersave`, а короткий кадр — ровно тот случай, где видно разгон частоты. Поэтому эти числа не сравнимы напрямую с прогонами на холостом режиме. Турбо при этом включён, частота не закреплена, поэтому wall-время зависит от boost- и теплового состояния вокруг запуска. Медианы это уменьшают, но не убирают. Свип снят на в остальном свободной машине; ни один конкурирующий запуск здесь не публикуется.
- Wall-время включает фиксированную стоимость на процесс (старт, загрузка бинарника, проекция геометрии), а не только цикл по тайлам. `NT_PPM=0` убирает файловый ввод-вывод PPM, так что это время целого запуска программы, а не ядра растеризатора.
- Одна машина, один компилятор, одна сборка, одна сцена. Второго бэкенда или компилятора для сравнения нет.
