# Журнал

Хронология работы: что пробовали, что сломалось, чем починили. Ошибки
приводятся дословно — по ним потом ищут в поиске. Подробный справочник по
языку, собранный отдельным исследованием, лежит в `docs/language-notes.md`;
здесь — только то, на что наступил этот проект.

## 2026-09-18

### Установка и стенд

`curl -fsSL https://bend-lang.com/install.sh | sh` поставил Bend 2.0.5.
Лончер пишет своё состояние в `~/.bend` (`rep`, `last`, `id`), а эта рабочая
среда держит `$HOME` только для чтения, поэтому каждый запуск печатал
`cannot create /home/user/.bend/last`. Завели `tools/bend` — обёртку,
которая переносит `BEND_HOME` внутрь рабочей копии и выключает телеметрию.

Проверено сразу: `!` (GPU-вызов) собирается clang 18, хотя гайд просит 19+;
`.gpu`-файл не создаётся. Причина — молчаливая CPU-сборка на clang 18, а не
отсутствие GPU: на хосте стоит RTX 4090 Laptop. Настройка CUDA и две легко
путаемые ошибки выписаны в `AGENTS.md`.

### Законы и доказательства: ворота работают

Первым делом собрали минимальную пару `LAWS`/`PROOF` из гайда (`add_zero`
на `Nat`). `All terms check.` — и, что важнее, заведомо неверный закон
падает с внятным текстом:

```
- expected : Nat.add(x, 1n)
- observed : x
```

Это главная причина, по которой язык вообще интересен: ошибка печатает
`expected`/`observed` и место, а не «type mismatch».

### Порт: что сломалось и почему

Писали рендер инкрементально, компилируя после каждого шага. Ниже — ошибки
в порядке появления. Почти каждая — не «баг», а следствие правила, которое
надо знать заранее.

**1. Операторы без аннотации принадлежат `Nat`.**
`F32.abs(px - tx : F32)` — ошибка `expected : a term / observed : ':'`.
Аннотация обязана быть в скобках: `F32.abs((px - tx : F32))`. И наоборот,
`(a : F32) * b` тоже неверно: `*` оказывается **вне** аннотации и уходит в
`Nat`. Правило: каждый арифметический аргумент вызова и каждое арифметическое
тело `def` заворачивается в `( … : T )` целиком.

**2. Сравнения `>=` внутри `( … : Bool )`.**
`(ax >= ay : Bool)` компилятор разворачивает в `Bool.is_ge`, которого нет:
`expected : a defined name / observed : Bool.is_ge`. Сравнение на F32 надо
называть явно: `F32.is_ge(ax, ay)`. Скобки `: Bool` нужны только для `&&`/`||`.

**3. Деструктуризация — только параметр.**
Три разные ошибки подряд:

```
- a match cannot scrutinize a computed value: give it its own def
- a match cannot scrutinize a local binder: give it its own def
```

То есть `V3{x, y, z} = call()` и `V3{x, y, z} = local` запрещены, а
`V3{x, y, z} = parameter` — можно. Обход: функции-аксессоры (`V3.px`,
`V3.py`, `V3.pz`) или отдельный `def` с нужным параметром.

**4. `let` перед `match` по параметру.**
`+h2 = …` затем `match up:` →
`match scrutinees in binder order (this variable is unbound, consumed, or out
of order: reorder the match)`. Сначала `match`, потом `let` внутри ветки.

**5. Взаимная рекурсия запрещена, и это ломает привычный рефакторинг.**
Самая дорогая находка. Хотелось вынести разбор `Bool` в отдельный `def`:

```python
def march(...):
  march.if(stop, ...)          # нельзя
def march.if(stop, ...):
  march(...)                   # и это нельзя
```

`expected : a defined name / observed : Scene.march.if` — определения обязаны
идти **до** использования, а пара «обёртка ↔ помощник» образует цикл.
Правильный способ — вложенный `match` в одном `def`, принимающем `Bool`
**параметром**:

```python
def march(+i: Nat, +stop: Bool, …):
  match i:
    case 0n: t
    case 1n+k:
      match stop:
        case True{}: t
        case False{}: … march(k, …)   # себя — можно
```

Так же пришлось переписать обход строки квадродерева (`Px.row`).

**6. Многоscrutinee-`match` требует все комбинации.**
`match d img:` с ветками `0n Pix{c}` и `1n+e Qua{…}` падает:
`expected : cases for Qua`. Нужны все четыре сочетания, либо (проще) вложенные
`match` друг в друга.

**7. `match` — не выражение.**
В `do`-блоке:
`expected : a term (a match heads a def body, not a term)`.
Лечится выносом в отдельный `def`.

**8. `do`-блок: `let` без аннотации ломает блок молча.**
```python
do IO<Unit>:
  +v = F.c(1, 2)      # блок на этом заканчивается
  IO.print(...)        # expected 'def', 'type' or 'law', observed 'I'
  IO.print(...)        # и это уже вне блока
```
С `v : U32 = F.c(1, 2)` тот же блок работает. Отдельно: **деструктуризация
кортежа в `do` — не инструкция**. `(f, r) = fr` разбирается как возвращаемое
значение блока, и хвост блока отваливается. Лечится выносом распаковки в
`def`, где кортеж — параметр.

**9. Алгебра имён при импорте.**
`import ./scene.bend as Scene` даёт доступ к имени `Scene.` + **полное**
имя `def`. То есть `import ./color.bend as Color` и `def Color.pack` дают
`Color.Color.pack`, а короткое `Color.pack` — `expected : a defined name`.
Пришлось убрать внутренние префиксы: в `color.bend` это `pack`, `red`,
`green`, а снаружи — `Color.pack`.

**10. Типы аргументов у сдвигов.**
`U32.shln(a: U32, n: Nat)`, `U32.shrn(a: U32, n: Nat)`. Литерал `1` — это
`U32`, поэтому `U32.shrn(half, 1)` не компилируется: нужен `1n`.

**11. Порядок объявлений — часть программы.**
После каждой правки приходилось переставлять `def`, поэтому появился
`tools/order.py`: он строит граф ссылок между верхнеуровневыми элементами
файла и сортирует их топологически, а на цикле печатает виновную цепочку.
Именно он поймал `Px.row → Px.row.sel → Px.row`.

**12. Мелочи синтаксиса, стоившие по компиляции каждая.**
- `Qua{tl: a, tr: b, …}` — именованные поля в конструкторе не поддерживаются,
  только позиционно: `Qua{a, b, c, f}`.
- `def Laws.frame8:` — нужны скобки: `def Laws.frame8():`.
- Равенство в `law` должно быть на одной строке: перенос внутри `{ … : Nat}`
  даёт `expected : a term / observed : ':'`.

**13. Affine-использование — самая частая ошибка.**
`expected : cars / observed : cars (consumed more than once)`. Всё, что
используется дважды, помечается `+`: параметры (`+cars`), поля в образце
(`Car{+cc, +ss, …}`), привязки (`+img : Image = …`). При этом `+` требует
`Data`: на функции его не поставить.

### Что получилось

Первый кадр вышел белым: `Cam.fit` переписывал камеру, но `cx`/`cy`
(центр экрана) брал из **входной** камеры, где они нулевые, — деление на ноль
дало `dir=nan,nan,nan`, а `F32.clamp` от NaN вернул 1.0, то есть белый.
Второй кадр вышел перевёрнутым: строки PPM собирались от последней к первой,
а `++` дописывает в конец. Обе ошибки нашлись за один прогон, потому что
рендер печатает контрольный код и складывает PPM — смотреть было на что.

### Публикация в хаб: как одна ошибка процесса ушла наружу

Агент, писавший `docs/language-notes.md`, в ходе исследования тулчейна
выполнил `bend tiny.bend --publish`. Файл — 79 байт, `import Base` и
`IO.print("compile me")`, ничего проектного. Но он **остался в публичном
хабе навсегда**: `https://hub.bend-lang.com/0xdc5e239cf0bf288e1735d5852f820f34/tiny.bend`.

Отозвать нельзя по устройству сервиса, а не по недосмотру: «no accounts, no
names, no versions», ответы отдаются с `cache-control: immutable`, личности,
которой можно авторизовать удаление, не существует. В клиенте нет обратной
операции.

Что сделано: `tools/bend` теперь отказывает на `--publish` (код возврата 2) и
пускает только при `BEND_ALLOW_PUBLISH=1`, который выставляет человек. Правило
записано в `AGENTS.md`.

Что было сделано неправильно: субагент получил доступ к инструменту с
необратимым публичным действием, и предохранителя на нём не было. То, что
улетел безобидный hello, — везение.

### Второй рендерер: ray marcher становится растеризатором

Ray marcher рисует кадр 512x512 за 0.30 с на 16 потоках. Это один статичный
кадр в три секунды, а просили версию, которую можно смотреть. Старый рендерер
перенесли в ветку `legacy/raymarch` (тег `raymarch-legacy`), а основная ветка
получила тайловый растеризатор: `src/raster.bend` с `rt.bend` (типы, камера,
проекция, отсечение), `shade.bend` (фрагмент и небо), `world.bend`, `inst.bend`,
`carriage.bend` (супы треугольников), `ride.bend` (камера и свет), `geo.bend`,
`trk.bend`. Кадр по-прежнему одно квадродерево и по-прежнему единственное место,
где делится работа, но лист — это тайл 8x8 пикселей, несущий треугольники, чей
экранный bounding box до него дотягивается, и пиксель закрашивается ровно один
раз — треугольником, который его выиграл.

Ray marcher на этой ветке не балласт: это единственный рендерер, у которого
пиксель — чистая функция пикселя, и законы формулировались именно на нём.

### Сглаживание, которое стало самой крупной отдельной ошибкой

Демо просит у WebGL `antialias: true`, то есть 4x MSAA, а у растеризатора его,
конечно, не было: края были жёсткие, и разница с эталоном сосредоточилась ровно
там. Четыре сэмпла на пиксель со смещением +-0.25 в `Tile.px`, усреднение в
упакованном `U32` (`Px.avg4`), а не во float, — вот и вся правка. На 1024x1024:
MAE 0.002187 -> 0.001850, PSNR 40.71 -> 43.17 dB. На 512x512: 0.002716 ->
0.002056, PSNR 42.24 dB. Стоит около 12% кадра глубины 8.

### Текстовый эмиттер стоил дороже рендера

Живой просмотр пишет P3 (ASCII) PPM, и числа в нём не бесплатны: текст занимал
70–80% живого кадра. Три изменения, каждое сверялось с неизменившейся картинкой
(побайтово идентичные PPM на глубине 6):

- `IO.write` на тайл вместо склейки тайлов строки на каждом уровне дерева
  (`String.concat` — правая свёртка, поэтому сборщик строки копировал её по разу
  на тайл);
- десятичный эмиттер, который пишет цифры прямо в остаток строки
  (`Px.dig.one/two/three`), вместо прохода через `U32.show`, а тот стоит примерно
  вчетверо дороже на пиксель;
- один cons-проход справа налево на тайл (`Tile.text(xs, tail)`), так что ни одна
  строка канала не строится и потом не копируется.

Глубина 9 — с примерно 0.64 с до 0.34 с на кадр, глубина 8 — с 0.27 до 0.19.

### `!` компилируется, ничего не меняет и стоит трети секунды на процесс

`probes/bench/bang.bend` выясняет, что `!` делает здесь: однородное дерево F32
под `!` показывает 0.00–0.01 с host CPU при любом числе потоков, а то же дерево
без `!` — 0.17–0.20 с и масштабируется с `--threads`. Рекурсию держит устройство;
это и есть характерный признак.

Собственное дерево растеризатора ведёт себя иначе. `Frame.build!(...)` собирает
cubin на 498 KB как `out/night-train.gpu` и возвращает *тот же самый дайджест* на
любой глубине — глубина 10: `3959815329` в обоих случаях, — но время host CPU
одинаково и с ним, и без него (глубина 10, 32 потока: 4.12 с против 4.43 с). Лист
рендерера дивергентный — каждый тайл обходит разное число треугольников, — а это,
по гайду, та форма, что остаётся на CPU, тогда как дерево этого пробника
однородно.

Решила дело цена самого тега. Программа, содержащая `!`, собирает программу для
устройства и **загружает её при каждом старте процесса**: тот же рендерер с тегом
отрисовывал кадр глубины 8 за 0.45–0.51 с, а без него — за 0.15–0.16 с, при любом
числе потоков, — около 0.3 с на процесс, потраченных ещё до начала работы.
`tools/live.sh` запускает один процесс на кадр, так что тег не давал ничего, а
стоил втрое дороже. Драйвер, параметр `bang` у `frame.chunks`, `Frame.build.at` и
всю обвязку `NT_BANG` удалили, устаревший `out/night-train.gpu` убрали, а
дайджесты перепроверили — они не изменились (глубина 8 `299380445`, глубина 9
`1065901264`, глубина 10 `3959815329`). Пробник остаётся: это единственное место,
где ещё меряется полоса устройства.

Этот разбор попутно дал одну находку про язык. `match` обязан рассматривать свои
привязки в том порядке, в каком они связаны, поэтому двухветочный `match` по
флагу не мог стоять после камеры и сцены, где ему было место:

```
- message  : match scrutinees in binder order (this variable is unbound,
             consumed, or out of order: reorder the match)
```

Его вынесли в собственный `def`, `Frame.build.at`, тело которого — этот `match`,
а первый параметр — флаг; и именно этот `def` потом удалил замер, о котором речь
выше.

### Живой просмотр и сколько стоит кадр

`tools/live.sh` отрисовывает собственную поездку демо в stdout как поток P3 PPM,
по одному кадру на процесс, и отдаёт его в `ffplay`: рендер можно смотреть прямо
во время работы. На бинарнике без `!`, на 24 потоках:

| | глубина 8 (256x256) | глубина 9 (512x512) |
|---|---|---|
| один процесс на кадр | 178 ms | 228 ms |
| десять кадров в одном процессе | 205 ms | 309 ms |

То есть живой просмотр идёт на **5.6 fps при 256x256 и 4.4 fps при 512x512**,
причём на глубине 8 быстрее оказывается форма «один процесс на кадр» — кадр
достаточно короткий, и повторный разбор стоит меньше, чем лишнее состояние
пакетного режима. Из этих 178 ms сам рендер — 155 ms, а ASCII-эмиттер десятичных
чисел — оставшиеся 23 ms: после работы над эмиттером выше запись PPM больше не
узкое место.

### Видео-сравнение

Одного статичного кадра с каждой стороны было недостаточно, поэтому
`tools/compare_video.sh` записывает поездку дважды — рендерер на Bend и
оригинальное демо, — и складывает два клипа кадр к кадру в
`assets/video/compare-512.mp4`, а рядом кладёт постер-кадр и анимированный GIF.
Обе камеры
— закреплённая камера сравнения (`s = 110 + 24.5 t`, yaw 0, pitch -0.02, без
качания), и клип идёт на 25 fps, потому что 1000/25 — ровно 40 ms: на 24 fps
целочисленно-миллисекундный шаг времени рендера округляется до 41 ms, и к концу
восьми секунд стороны расходятся на три метра.

Чтобы его снять, пришлось решить две инструментальные проблемы:

- `tools/render_reference.py` обзавёлся последовательностью `--frames`. Один кадр
  на процесс стоил 5.5 с, из которых около 4 с — запуск браузера; последовательность
  делит один браузер и платит около 0.4 с на кадр, так что 200 кадров занимают две
  минуты вместо восемнадцати.
- `tools/video_frames.py` складывает кадры тем же подписанным сравнением бок о
  бок, которое `tools/compare.py` рисует для статичного кадра, так что видео и
  сравнение статичных кадров — одна и та же картинка и разойтись не могут.

Первый заход на последовательность оказался неверным, и это поймали числа. Кадр 0
клипа совпадал со статичным кадром до последней цифры (MAE 0.002056), а дальше
ошибка нарастала по клипу — 0.0036, 0.0093, 0.0516, — тогда как сторона рендера в
каждом кадре была побайтово идентична одно-кадровому рендеру с той же камеры.
Дрейфовала именно сторона эталона: частицы и дым демо — это **stateful**-массивы,
которые обновляет его draw call, поэтому кадр *i*, отрисованный после кадра
*i-1*, — не та же картинка, что свежая страница с той же камерой. Сидирование не
помогает — восстановление PRNG между кадрами ничего не меняет, потому что
состояние живёт в массивах, а не в генераторе. А вот страница на каждый кадр
помогает: тогда кадры побайтово идентичны статичным, по 0.4 с каждый. Сравнение
честно ровно настолько, насколько честен эталон, и клип с дрейфующим эталоном
показал бы этот дрейф как нашу ошибку.

После пересъёмки все 200 кадров клипа укладываются между 0.0021 и 0.0037 MAE
относительно эталона: покадровое дрожание — это проезжающая мимо сцена, а не
дрейф.

### Демо отсекает состав, а здесь отсечение только хуже

Эталон включает `CULL_FACE` для всего, кроме пути
(`docs/reference-demo-spec.md` §5.4). Растеризатор отсекал только землю, поэтому
исправление выглядело очевидным: разделить сцену на три части (земля, путь,
остальное) и отсечь последнюю. Измеримо *хуже* — 512x512 MAE 0.002056 ->
0.004961, PSNR 42.24 -> 37.19 dB, — а это говорит, что намотка состава и
инстансных мешей не как в демо и что обе их грани надо рисовать, чтобы попасть в
ту же картинку. Откатили, а число записали в `Raster.frame`.

### Что всё ещё не так: одна полоса ближнего вагона

На 512x512 кадр совпадает с эталоном до 1/255 почти везде, а остаток
сосредоточен в одной полосе борта ближнего вагона (x 0..56, y 168..194) плюс
подсвеченные края окон. В этой полосе нормаль фрагмента смотрит строго вверх —
замерено возвратом нормали из `Shade.Sh.v` в черновой сборке:
`N = (+0.14, +1.00, +0.01)`, — а эталон показывает там зелёную стену. Нормаль
вверх берёт верх полусферического ambient — синий край — и совсем не берёт свет
окон, а это ровно не тот цвет и недостающее тепло. Значит, причина не в затенении
(тот же шейдер верен уже на соседнем тайле), а в том, какой треугольник выигрывает
эти пиксели. Отсечение не помогает — см. выше, — и сначала надо разобраться с
собственной намоткой меша. Записано, не исправлено.
